# ListMate Security & Encryption Architecture

This document outlines the security posture of the ListMate application, specifically focusing on data encryption (both at rest and in transit) and the security of our APIs.

## 1. Encryption at Rest

**The Concept:**
Encryption at rest refers to protecting data when it is stored on a physical or virtual disk (e.g., SSDs, hard drives, or backup storage). If a malicious actor were to gain physical access to the storage media, or if they managed to exfiltrate a database snapshot, the data would remain unreadable without the specific decryption keys.

**Our Implementation (Render PostgreSQL):**
ListMate's primary data store is hosted on [Render's managed PostgreSQL](https://render.com/docs/databases).
*   **AES-256 Encryption:** Render provisions its databases on top of major cloud providers (AWS or Google Cloud). By default, all block storage volumes backing Render PostgreSQL databases are encrypted at rest using the industry-standard AES-256 encryption algorithm.
*   **Backups & Snapshots:** Automated backups and point-in-time recovery snapshots generated by Render are also fully encrypted at rest.
*   **Key Management:** The encryption keys are managed transparently by the underlying cloud provider's Key Management Service (KMS), which rotates them automatically. This minimizes overhead while ensuring strict compliance with modern security standards.

## 2. Encryption in Transit

**The Concept:**
Encryption in transit ensures that data moving across networks—whether it's across the public internet or within an internal data center network—is cryptographically scrambled. This prevents Man-in-the-Middle (MITM) attacks, eavesdropping, and packet sniffing.

**Our Implementation:**
*   **Client to Server (HTTPS/TLS):** All communication between the ListMate mobile/web clients and our Python/Flask backend APIs happens strictly over HTTPS. We use modern TLS (Transport Layer Security) protocols (TLS 1.2 or 1.3). Render automatically provisions, manages, and renews our SSL/TLS certificates via Let's Encrypt. Any raw HTTP requests are automatically redirected to HTTPS.
*   **Server to Database:** The connection between our backend application and the Render PostgreSQL database occurs over a securely encrypted internal network. We enforce TLS for the database connection strings, ensuring that even within the Render infrastructure, the SQL queries and result sets are encrypted while traversing the internal network.

## 3. API Security & Authentication

**Secure Transport:**
As mentioned, all API endpoints (`/api/*`) are exposed exclusively over HTTPS, preventing credentials or sensitive payload interception.

**Identity and Access Management:**
*   **Google Sign-In (OAuth 2.0):** We do not handle, hash, or store user passwords. We rely entirely on Google Sign-In for authentication. The client receives a secure JWT (JSON Web Token) from Google, which is then sent to our backend.
*   **Token Verification:** Our backend actively verifies the integrity, audience, and cryptographic signature of the Google token before issuing an internal session or fulfilling a data request.
*   **Household Isolation (Tenant Isolation):** API endpoints strictly enforce authorization checks based on the `household_id` bound to the authenticated user's session. Users can only read, write, or modify data (like grocery lists and store visits) that belong directly to their specific household. 
*   **AI Data Privacy:** When interacting with the Gemini API for Chef AI or Shopping Insights, we strip personally identifiable information (PII). Only anonymized data (e.g., aggregate store visit counts, item names) is transmitted to Google's generative models, and this data is explicitly opted out of model training per Google's enterprise API terms.

## Summary
By combining Render's AES-256 encryption at rest, mandatory TLS 1.2+ for all network communications, and stateless token-based Google Authentication, ListMate maintains a robust, enterprise-grade security posture suitable for protecting users' personal household data.
